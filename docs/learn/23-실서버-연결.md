# 23. 진짜 서버에 연결하기 — 테스트에서 실제 서비스로

지금까지 브라우저 테스트는 **가짜 서버**(`tests/e2e/fake-supabase.mjs`)로 돌렸어요.
이제 같은 앱을 **진짜 Supabase**에 붙여요. 순서가 중요해요.

## 1) 서버 규칙(SQL)을 먼저 적용

`supabase/migrations/001_b_stage.sql`이 서버의 "규칙집"이에요.

- 표 4개: `bottles`(병), `replies`(답글), `likes`(좋아요), `reports`(신고)
- 표는 잠가 두고(RLS 켜기 + 권한 회수), 앱은 **정해진 함수 7개**로만 읽고 써요.
  - 예: `list_bottles`, `create_bottle`, `like_bottle`
  - 그래서 누가 공개 키를 가져가도 표를 통째로 지우거나 남의 기기 토큰을 볼 수 없어요.
- 이 파일은 내 컴퓨터의 PostgreSQL에서 **두 번 연속 실행**하는 테스트를 통과했어요. 실수로 두 번 붙여 넣어도 안전해요.

왜 먼저일까요? 앱을 먼저 올리면, 서버에 아직 함수가 없는 동안 모든 사람 화면에 "바다 소식을 불러오지 못했어요"가 떠요.

## 2) 앱 올리기(Push)

GitHub Desktop에서 Commit → Push. 폰 브라우저 캐시 때문에 **10분쯤 뒤** 새로고침해요.

## 3) 진짜 서버에서 확인할 것

1. 병 하나 띄우기 → 링크 받기
2. 다른 기기(또는 앱 데이터를 지운 새 탭)에서 그 병이 보이는지
3. 병을 눌러 카드 열기 → ♥ 누르기 → 숫자가 오르는지
4. 확인용 병은 Supabase Table Editor에서 지우기(`docs/deploy.md` "이상한 병 지우기")

## 4) 서버가 잠들지 않게 — GitHub Actions

Supabase 무료 프로젝트는 **7일 동안 요청이 없으면 일시 정지**돼요.
그래서 `.github/workflows/keepalive.yml`을 만들었어요.
GitHub가 매일 한국 시간 오전 9:17에 `list_bottles`를 한 번 불러요.

- `cron: "17 0 * * *"` — 분 시 일 월 요일 순서예요. 시간은 UTC 기준이라 한국(+9시간)으로는 09:17이에요.
  정각(00분)을 피한 건 GitHub에 예약이 몰리는 시간이라 늦어질 수 있어서예요.
- `workflow_dispatch` — Actions 탭에서 **Run workflow** 버튼으로 손으로 돌려볼 수 있어요.
- 들어간 키는 앱에도 있는 공개 키라 괜찮아요. 관리자 키는 GitHub에도 넣지 않아요.

## 비밀은 어디에도 적지 않는다

| 무엇 | 어디에 |
|---|---|
| 공개 키(publishable) | 코드(`src/net/config.js`), keepalive — 공개돼도 됨 |
| 관리자 키(secret) | **어디에도 안 씀** |
| DB 비밀번호 | 세민님만 앎. 코드·문서·채팅에 안 씀 |

공개 키로 할 수 있는 일은 SQL에서 열어 준 함수 7개뿐이라, 키가 보여도 안전하도록 **서버 쪽에서** 막아 둔 거예요.
